# BSA03562001091 Negative GMP Reproduction

## Goal

Reproduce, step by step, how production data is transformed into the negative `GoodMaterialProduced` value for `BSA03562001091`.

This document follows the same logic as `GMP.md`, but instead of a synthetic example it uses the real production case and the exact queries needed to rebuild the path.

## How To Read This Document

Use this document in three passes:

1. Read **Final Formula** and **Database-To-Negative Story In One Line** first. This gives the high-level model.
2. Read **Worked Production Case** from Step 1 to Step 9. This shows the processing path from shifts, jobs, events, and telemetry to the negative value.
3. Use **Debugging Checklist** to repeat the same method for another equipment.

The most important mental model is:

```text
The negative value is not a direct event field.
It comes from selected boundary counters.
For a historical incident, those counters must be reconstructed with the data visible at generation time.
```

## Final Formula

On `master`, the displayed value is computed here:

- `Backend/Services/OeeCalculation.cs`, `CalculateQuality(...)`

Formula:

`GoodMaterialProduced = FinalTotalOutputTelemetry - InitialTotalOutputTelemetry - ManualRejectionCount`

Important consequences:

- `GoodMaterialProduced` is not taken directly from `TotalOutput`.
- `AutomaticRejectionCount` is not subtracted directly from `GoodMaterialProduced`.
- The key incident question is which start and end counters were available to the job when the report was generated.

## Database-To-Negative Story In One Line

```text
notificationConfiguration
-> daily report UTC period
-> shift templates
-> job / timeshift / material rejection events
-> EventList
-> EventRanges
-> shift chunks
-> start/end boundary counters as of generation time
-> aggregated counters
-> GoodMaterialProduced = final - initial - manual rejection
-> negative value
```

## Main Concepts

### What is `generationUtc`?

`generationUtc` is the UTC time when the report job generated the daily report.

It matters because the job did not see the final retained dataset. It saw only the rows already ingested by that time.

### Why `ingestion_time()` matters

For a historical incident, `Timestamp` alone is not enough.

The report job saw only rows matching:

```kusto
| extend IngestionTime = ingestion_time()
| where IngestionTime <= generationUtc
```

This is the difference between:

- current retained state
- historical as-of-generation state

### Shift templates vs shift events vs job events

These are different layers of data:

- shift templates come from `timeshifts`
- timeshift events come from `events`
- job start events also come from `events`

The service first needs the shift templates to know which shifts overlap the report period, then it combines those with timeshift events, job events, and telemetry.

### What is a chunk?

A chunk is the intersection between:

- the requested report period
- and one overlapping shift

The algorithm calculates counters per chunk, then aggregates them.

## Process Overview

End-to-end flow for this incident:

```text
1. Resolve the daily report period from notificationConfiguration and timezone
2. Load shift templates from timeshifts
3. Load jobs, timeshift events, and material rejection events from events
4. Convert those raw rows into EventList
5. Convert EventList into EventRanges
6. Split the report period into shift chunks
7. Resolve start/end boundary counters with generation-time visibility in mind
8. Aggregate counters and subtract manual rejection
9. Compute the final GoodMaterialProduced value
```

## Boundary Selection Decision Tree

For each chunk, the algorithm needs a start boundary and an end boundary.

Decision flow:

```text
1. Is there an exact usable TimeshiftEvent or job boundary event?
   Yes -> use it as the boundary.
   No  -> create a virtual boundary from telemetry.

2. If a virtual boundary is needed, is the requested boundary affected by data loss?
   Yes -> the lookup direction can change.
   No  -> use the closest telemetry before the boundary.

3. For a historical incident, was that telemetry already ingested at generationUtc?
   Yes -> it was visible to the report job.
   No  -> it did not exist yet for that report run.

4. If the initial boundary exists but the final one is missing, a negative GMP becomes possible if the missing final value becomes 0.
```

### Step 3A: Get The Last Active Job Before Report Start

Why this query exists:

```text
If a job was already running when the report period started, the job start event can be earlier than reportStartUtc.
```

Verification query:

```sql
SELECT TOP 1 c.timestamp AS startJobEvents
FROM c
WHERE c.equipmentId = @equipmentId
AND c.timestamp < @startDate
AND c.type = 'newJob'
```

## Step 6: Resolve The Start Boundary As Of Generation Time

Code:

- `Backend/Services/OeeCalculation.cs`, `GetCounterAndEventsAsyncForTimePeriod(...)`
- `Backend/Services/ShiftManagementService.cs`, `GetShiftEventWithNewTelemetryData(...)`
- `Backend/Repositories/HotTelemetryRepository.cs`, `GetMostRecentTelemetryAsync(...)`

What happens:

- daily reports query the hot path first, which means `telemetryhours`, not ADX
- if no exact shift event or job event can provide the boundary counter, the service creates a virtual shift event from hot telemetry
- `ShiftManagementService.GetTelemetryDataBasedOnDataLoss(...)` chooses the lookup direction:
  - default branch: closest telemetry in the past, `timestamp <= @date`, `ORDER BY timestamp DESC`
  - data-loss branch: first telemetry in the future, `timestamp >= @date`, `ORDER BY timestamp ASC`
- for this incident, the start boundary behaves like the `After` branch, so the first usable hot-path row is after `reportStartUtc`

Hot-path verification query:

```sql
SELECT TOP 1 VALUE {
   timestamp: t.timestamp,
   totaloutputunitcount: t.totaloutputunitcount,
   totalproductiontime: t.totalproductiontime,
   machinestate: t.machinestate,
   ts: t._ts
}
FROM c t
WHERE t.equipmentId = @equipmentId
AND t.timestamp >= @date
AND IS_DEFINED(t.totaloutputunitcount)
AND NOT IS_NULL(t.totaloutputunitcount)
AND t.totaloutputunitcount > 0
ORDER BY t.timestamp ASC
```

Parameters for this case:

```text
@equipmentId = BSA03562001091
@date = 2026-05-10T03:00:00Z
generationUtc = 2026-05-11T03:02:00Z
```

Note:

```text
The application does not query `_ts`.
We add `_ts` only to reconstruct whether the hot-path document already existed at generation time.
```

Important hot-path result:

```text

AvailableAtGeneration: yes
Output:                32,225,530
```

Interpretation:

### Step 7C: Historical Cross-Check That Report End Was Inside A Telemetry Gap

Verification query:

```kusto

| union lastValues
| where count_ > 0
| order by Timestamp asc
| serialize
| extend PreviousTelemetry = prev(Timestamp)
| where isnotnull(PreviousTelemetry)
| extend GapStart = PreviousTelemetry + interval,
         GapEnd = Timestamp
| extend Duration = GapEnd - GapStart
| where Duration >= 5m
| extend OverlapsReportEnd = GapStart <= reportEndUtc and GapEnd >= reportEndUtc
| project GapStart, GapEnd, Duration, OverlapsReportEnd, PreviousTelemetry, NextTelemetryOrSynthetic = GapEnd
| order by GapStart asc
```

## Step 8: Aggregate Counters And Apply Manual Rejection

Code:

- `Backend/DataObjects/OeeCounters.cs`, `IncrementCounters(...)`
- `Backend/Domain/Oee/MaterialRejectionCalculation.cs`

What happens:

- chunk counters are aggregated
- the first initial telemetry is kept
- the final telemetry is overwritten by the last chunk's final telemetry
- manual rejection is subtracted at the end

For the exact negative reproduction, the only production facts needed here are:

| item | value |
| --- | --- |
| InitialTotalOutputTelemetry | `32,225,530` |
| FinalTotalOutputTelemetry at generation time | `missing` |

This is the minimum state needed before applying the GMP formula.

## Step 9: Reproduce The Negative Value

Apply the production facts to the formula:

```text
GoodMaterialProduced = FinalTotalOutputTelemetry - InitialTotalOutputTelemetry - ManualRejectionCount
GoodMaterialProduced = 0 - 32,225,530 - 0
GoodMaterialProduced = -32,225,530
```

That matches the email exactly.

## Why Current Replay Can Look Positive

If you replay with the current retained dataset instead of the as-of-generation dataset, the late row is already present:

```text
Timestamp:     2026-05-11 03:05:28Z
IngestionTime: 2026-05-11 03:06:41.8095624Z
Output:        32,435,826
```

That means the replay can see both boundaries and produce a positive value instead of the historical negative.

This is why the `ingestion_time()` filter is the key detail for reproducing this incident.

## Debugging Checklist

For another equipment, follow this exact order:

1. Get `dailyReportStartTime`, `dailyReportEndTime`, and the site timezone.
2. Build the UTC report period.
3. Load shift templates from `timeshifts`.

9. Materialize overlapping shift chunks.
10. Check start/end boundaries with `ingestion_time() <= generationUtc`.
11. Check whether report end sits inside a telemetry gap.
12. Aggregate counters and apply manual rejection.
